# VenueOS UI Status — Phase 3G

Tracks, per application, what each UI phase covers, which VenueOS components it uses, what's still missing, and where the layout has room for controls restored by the later functional-gap audit. This is a snapshot, not the gap audit itself. **Phases 1–3G were shell, component, and interior-visual work only** — Phase 4 is the first genuine functional reconstruction pass (Attendance + Greeter + VIP; see below and `RECONSTRUCTION_ATTENDANCE_GREETER_VIP.md`). The remaining six modules (ShoutRunner, Party Finder, Raffle, Mair's Trivia, TournamentControl, Bingo) are still visual-only; their standalone donor plugins remain the authoritative functional reference for whichever reconstruction pass reaches them next. **This is a narrow feature addition, not a new sign-off** — the user is performing final in-game acceptance separately; this document is not claiming the shell is frozen on its own authority.

## Phase 4 — Functional Reconstruction: Attendance + Greeter + VIP

The first module-behavior (not just chrome) reconstruction pass, driven against `C:\FFXIVplugs\venuestatusandgreet` (read-only donor reference; VIP has no donor — its requirements come from the reconstruction brief itself). It ran in two rounds: an initial pass that deliberately scoped down the donor's SQLite-backed history subsystem and its variable-size preset library, and a **correction pass** that revoked both deferrals and brought Attendance and Greeter to full standalone parity. Full gap analysis, the (now-superseded) original scoping decisions, and the correction pass's reasoning all live in `RECONSTRUCTION_ATTENDANCE_GREETER_VIP.md`; this entry describes the final state.

- **Full persisted session ("opening") lifecycle.** `AttendanceService` now supports Start New Opening / Pause (resumable) / Resume(a specific past opening) / Close / Delete, backed by a new SQLite database (`SqliteVenueDatabase`, Microsoft.Data.Sqlite 10.0.11 — current and unflagged, replacing the donor's advisory-flagged 9.0.3 pin) at `<plugin config dir>/attendance.db`, with every table scoped by venue id (the donor was single-venue and never needed this).
- **Full visitor history and analytics.** Tonight Summary (Current/Max/Min/Unique/Visits/Avg-per-guest), Tonight Visitors (searchable, present/greeted/departed styling, Target and Mark Greeted row actions), cross-night Max/Min guest comparison with an adjustable day range, 5-minute guest-count sampling (gated by a configurable poll interval, matching the donor's exact "5-minute bucket, N-second minimum gate" cadence), and Excel export (ClosedXML 0.105.1, three sheets: DailyStats/Visitors/GuestSamples) are all live in a new four-tab Attendance app (Live/Visitors/History/Analytics), reusing a new `UiKit.LineChart` component ported from the donor's own hand-drawn chart rather than a new charting dependency.
- **Venue Details / address tracking restored.** Settings → Modules → Attendance gained In-game Address (editable, optionally auto-detected via a new `IVenueAddressProvider`/`DalamudVenueAddressProvider` reading DC/Server/District safely and Ward/Plot/Subdivision via the donor's own `FFXIVClientStructs.HousingManager` call, ported unmodified) and a Stats Poll Interval that now actually drives sampling cadence (previously present in the data model but unused).
- **Greeter's saved-preset library + hotbar assignment replaces the fixed five presets.** Any number of presets can be created/edited/deleted in Settings → Modules → Greeter; each of the five hotbar slots is independently assignable to any library preset (or left empty) from Settings, while the operational app's hotbar stays a pure click-to-activate control showing whatever's currently assigned — the donor's exact "library + assignable hotbar" model, reversing the first pass's fixed-five-slots simplification.
- **Auto Greet First Visit Tonight.** New Greeter Settings toggle: a guest's *first* arrival of the calendar night (tracked in the database, independent of session pause/resume/close boundaries) automatically queues the active preset's greeting; repeat arrivals the same night never re-trigger it. The operator's own character is tracked/counted like any guest but is excluded from this auto-trigger. VIPs are unaffected by this toggle — they're still greeted on every arrival via their own dedicated path.
- **Greeter got its missing timing and safety behavior.** A 2-second inter-guest delay and per-step presence re-validation (a guest who leaves mid-greeting is dropped cleanly instead of continuing to receive tells after they're gone) match the donor. `Line2`, `Line3`, and Command — present in the data model since Phase 1 but never exposed in any UI — are editable in Settings → Modules → Greeter.
- **Operational vs. persistent split enforced for all three**, and re-verified after the correction pass's UI rewrite: Attendance's four-tab live view stays operational, its filtering/address/poll-interval config lives in Settings; Greeter's hotbar stays operational, its full preset library/hotbar-assignment/Auto-Greet/timing config lives in Settings; the VIP roster stays operational, only the recognition-tell template lives in Settings. A dedicated test (`Attendance_greeter_and_vip_modules_route_draw_and_drawsettings_to_distinct_delegates`) proves each module's `Draw()` and `DrawSettings()` invoke genuinely different code, not a shared fallback.
- **VIP roster editing is complete, not add-only.** Edit/Disable/Enable/Remove (with a `Name @ World` confirmation) alongside Add/Search, all through a proper Add/Edit modal (`VipEditDialog`) rather than a permanently-visible inline form. VIP identity (Character Name/Home World) is editable, tracked by the record's original key through an edit so renaming never orphans or duplicates a record.
- **"Use Current Target" / target-fill.** `ITargetedPlayerProvider`/`TargetedPlayerLookup` (`VenueOS.Services`, backed by Dalamud's `ITargetManager`) lets both Add and Edit fill Name/World from whatever the operator has targeted, with a clear inline error for no target/non-player/unavailable world instead of a crash or a malformed record. Never auto-saves and never touches announcement/notes/enabled/channel.
- **Arrival order verified, not changed.** Presence → Attendance → VIP recognition tell → Greeter's normal active-preset greeting → VIP public shout/yell → Greeter finalizes greeted state was already correct before this reconstruction; `VipOrchestrationService.OnArrival` was narrowed during the correction pass to only act on VIP matches (the normal-guest greeting trigger moved to Auto Greet), but the VIP-specific ordering and Greeter's sole ownership of the greeted flag are unchanged and covered by tests.
- **Known remaining gap, reported rather than silently dropped:** the donor's "Examine"/"Adventure Plate" visitor context-menu actions require internal Dalamud agent pointers not used anywhere else in VenueOS and unverifiable without a live session; Target and Mark Greeted were implemented as the two available Visitors-tab row actions instead.
- **Tests:** 70 tests across the three test projects (up from 46 before this phase), including a dedicated `AttendanceStoreTests.cs` exercising the real SQLite persistence layer against `Data Source=:memory:` (session lifecycle, first-visit-tonight-per-night semantics, time accrual, pause/close finalization, greeted-flag tracking, per-venue isolation of samples/stats/presets/hotbar), plus rewritten `OperationsTests.cs`/`VenueProfileTests.cs` coverage for Auto Greet gating, the preset library exceeding five hotbar slots, and per-venue isolation of the live-reloaded Greeter/VIP/Attendance state through actual venue switches (not just persisted-payload isolation). All 70 pass.
- **Second correction pass (live-testing bug fixes):** the correction pass above shipped correct-looking code with three real bugs, all found and fixed after actual in-game testing: (1) Attendance never populated guests already standing in the venue when an opening started, including the operator — root cause was `PresenceService`'s continuous scanning (needed for VIP) never re-firing `Arrived` for someone who'd already been detected before the session existed, unlike the donor's tracker, which only scans while its venue is open at all; fixed with a new `PresenceService.ResetKnownPresence()` + `VipOrchestrationService.ResetProcessed()` coordinated from a new `AttendanceService.SessionOpened` event. (2) The VIP "+ Add VIP" button and (3) Greeter's "New Preset" button were both genuinely invisible — not a missing feature, a layout bug: `Forms.SearchBox`'s default full-width sizing pushed a `SameLine()`-chained button off the visible card, the exact class of bug this codebase's own `UI_STATUS.md` history already documents fixing in `TabletHeader` and the Diagnostics toolbar. Both fixed by reserving the button's width first. Manual "Mark as Greeted" (Attendance Visitors) was also wired into `GreeterService`'s actual queue/greeted state for the first time (it previously only wrote a display flag), and gained a right-click context menu alongside the existing button plus an explicit Greeted/Not Greeted badge. Five new tests cover all of this; see `RECONSTRUCTION_ATTENDANCE_GREETER_VIP.md`'s "SECOND CORRECTION PASS" section for the full root-cause writeups.
- **Third correction pass (Greeter-only):** the "no usable preset library" report persisted after the second pass's UI-width fixes because of one more real bug: `greet_presets` had a `UNIQUE(venue_id, name)` constraint that `SavePreset`'s insert path never handled, so saving a second preset with a name already in use threw an unhandled exception that `UiKit.SafeDraw` turned into a full-screen error card in place of the entire Greeter Settings page — looking exactly like "the library doesn't exist" from the operator's side. Fixed by dropping the constraint (preset `Id` is the real stable identity; names were never required to be unique) with a real migration for databases created by earlier builds, verified against a raw on-disk legacy database in a new test. Everything else in Greeter Settings (library, editor, hotbar assignment, Behavior) was already correct.
- **Not touched:** Party Finder, ShoutRunner, Raffle, Mair's Trivia, TournamentControl, Bingo, and the donor repository (confirmed via `git status` after all passes — no tracked file in `venuestatusandgreet` was modified; two stray `bin/Debug`/`obj/Debug` build-artifact folders from earlier read-only inspection remain, since deleting anything in that repository requires the user's own say-so).

## Phase 3G — Global "Auto Pop-Out Modules" setting

The first genuine global (venue-independent) VenueOS preference: **Settings → General → "Open modules in separate windows"**, off by default.

- **Storage:** new `VenueOS.Services/GlobalSettingsService.cs` — `GlobalSettings` (a record, currently just `AutoPopOutModules`), `IGlobalSettingsStore`, and `GlobalSettingsService`. Backed in `Plugin.cs` by `DalamudGlobalSettingsStore`, which persists through a **new, separate `Global` property** on the existing `VenueOsPluginConfiguration` (alongside the pre-existing `State` property that holds venue data) — not folded into venue state, so it's structurally impossible for this preference to be read or written per-venue by mistake. It survives plugin reload and venue switching for the same reason `VenueProfileService` and `GlobalSettingsService` share no code path at all.
- **Launch routing:** the single place a module launch from Home decides embedded vs. detached — `HomeScreen.LaunchModule` — now calls a new pure function, `ModuleLaunchRouting.Resolve(bool autoPopOutModules)`, returning `ModuleLaunchTarget.Embedded` or `.Detached`. Every module registered in `ModuleHost` funnels through this one call (`foreach (var module in modules.Modules)` in `HomeScreen.DrawGrid`); there is no per-module branch, so a future module inherits the preference automatically the moment it's registered. `ModuleLaunchTarget.Detached` calls the existing `ModuleWindowManager.Open(moduleId)` — the exact open-or-focus method the pop-out button already used, so a second click on an already-launched module focuses it rather than duplicating it, for free.
- **Settings tile exemption:** Home's Settings tile was already a separate code path from the module loop (it was never inside `modules.Modules`), so it's unaffected by construction — no extra guard was needed to keep Settings embedded-only.
- **Disabled modules:** `AppTile.Draw`'s existing `enabled` gate (`var clicked = enabled && ImGui.IsItemClicked();`, unchanged) already prevents a disabled tile from registering a click at all — the routing function is never even reached for a disabled module, embedded or detached.
- **`CanDetach` capability flag:** deliberately not added. Every one of the nine current operational modules already supports detaching uniformly via the existing `ModuleWindowManager`/pop-out button, so there is no real distinction to encode yet — adding a flag with only one possible value everywhere would be exactly the unneeded complexity the brief warned against. If a future module genuinely cannot detach, this is the natural extension point.
- **Detached window Settings gear:** untouched — still routes to `Settings → Modules → <module>` via `ModuleWindowManager`/`ModuleWindowHeader` exactly as built in Phase 3E, completely independent of this preference.
- **Tests:** `GlobalSettingsServiceTests.cs` (new, `VenueOS.Services.Tests`) covers the default-off value, that toggling updates the in-memory value, that it survives a simulated reload (a second `GlobalSettingsService` built from the same store), that turning it back off also persists, that setting the same value again doesn't re-write the store, and both `ModuleLaunchRouting.Resolve` outcomes — 7 new tests, all passing. The actual Home-click → embedded/detached rendering and disabled-tile behavior are ImGui-coupled UI flow with no existing test harness in this codebase (matching every prior phase) and were verified by code inspection instead: `AppTile.Draw`'s enabled gate and `ModuleWindowManager.Open`'s idempotent open-or-focus semantics are pre-existing, unmodified code paths that this phase's one new call site relies on rather than reimplements.

## Phase 3F — Global toolbar Errors indicator removed

The Errors/"Recent errors" dot and label were removed from `TabletHeader` entirely — the global toolbar now only ever shows Home, brand mark, active venue name (left) and the venue selector, Settings, Close (right). Nothing was lost: error/warning state is still fully available on Home's overview card (`VenueOperationsDashboard`, unaffected) and in full detail at Settings → Diagnostics (unaffected). `TabletHeader.Draw` no longer takes `DiagnosticsService`/`SettingsScreen` parameters, since it no longer needs to read error state or route clicks to Diagnostics. Removing the indicator freed its reserved width entirely to the drag region between the venue name and the venue selector — the same "reserve the right region first, absolute screen-space positions" approach from the last two passes is otherwise unchanged, just with one less element to reserve for.

## Phase 3E — Global toolbar simplification, Diagnostics overlap fix, detached-window chrome

### Global toolbar — now truly global

`TabletHeader` no longer names whatever screen happens to be open. The app/module breadcrumb ("… The Vat Settings", "… The Vat Greeter") is removed entirely — the toolbar is now identical regardless of what's open (Home, Settings, or any module), since each screen's own content (via `AppFrame`'s icon+name header) already identifies itself. This also simplified the header's flex region down to just a drag handle; there's no longer any content in it to degrade.

The Errors indicator moved from the left (next to venue identity) into the reserved right region, immediately left of the venue selector: `● Errors [The Vat ▼] [⚙] [X]`. It's built the same "reserve-first" way as the rest of the right region — its own width (full "● Errors" label vs. an icon-only dot) is the *only* thing that ever adapts, and even that is a last resort: the primary degradation path is now truncating the venue name (new — `TabletHeader.Truncate`, with the full name in a tooltip) so that Close/Settings/the venue selector/Errors virtually never need to shrink at all in practice. Clicking the indicator (dot or label) still routes to `Settings → Diagnostics` via the same `shell.SelectSettings()` + `SettingsScreen.FocusDiagnostics()` used before — no duplicated logic.

### Diagnostics toolbar overlap — root cause and fix

The previous toolbar mixed `Forms.SearchBox` (a single-line field) at the same absolute Y as `Forms.ComboField`'s label row (`ComboField` draws two lines internally: label, then field). Placing Search there, then falling through to normal auto-flow for the Clear/Copy buttons, meant those buttons were positioned against Search's *own* single-line height rather than the taller two-line combo columns beside it — so Clear/Copy rendered on top of the Module filter's actual dropdown field. The toolbar is now built like `TabletHeader`: the right action region (Clear, Copy) is reserved first from a fixed width; Log Level and Module are fixed-width and never shrink; Search gets whatever's left. If that's under 120px (only possible in the narrow Settings layout, i.e. a total width under 640px), the toolbar reflows Search onto its own second row below Log Level/Module/Clear/Copy instead of overlapping — every position in both layouts is an explicit absolute screen coordinate, not chained auto-flow.

### Detached module windows — native chrome removed

Every detached module window (`ModuleWindowManager`) now opens with `ImGuiWindowFlags.NoTitleBar | ImGuiWindowFlags.NoCollapse` — confirmed by grep to be the *only* two `ImGui.Begin` calls in the whole plugin, and both now lack a native title bar. In its place, a new shared `Shell/ModuleWindowHeader.cs` — one implementation, reused by every module, not reimplemented per window — draws: module icon + display name on the left (always shown in full; no global controls appear here per §25 — no Home, no Errors, no venue selector, no venue name), Settings gear + Close on the right (reserved in absolute screen space first, same pattern as `TabletHeader`), and a drag handle in the empty middle. Resize borders are untouched (no `NoResize` flag) so resizing still works with no title bar, exactly as already established for the main tablet.

- **Icon/name:** reads `module.Descriptor.Icon`/`DisplayName` directly — the same values Home tiles and the Modules Settings table use, so a module has exactly one visual identity everywhere (§27 was already true by construction; this just extends it to the one remaining place that hadn't used it, since the old detached title bar used to build its own string).
- **Settings routing:** the gear now calls a new `SettingsScreen.FocusModuleConfiguration(moduleId)` (jumps to Settings → Modules and calls `ModulesSettingsPage.OpenConfigure(moduleId)` — the exact method the embedded Modules page's own "Configure" button already used) plus a new `Plugin.RequestOpenAndFocusTablet()` (the same open-or-focus logic `/venueos` uses, extracted so both share it) if the main tablet is currently closed. Never opens a second tablet.
- **Close:** sets a local `closeRequested` flag checked after `ImGui.End()`, removing only that module from `ModuleWindowManager`'s open set — does not touch `IVenueModule.IsEnabled`, module business state, the active venue, or the main tablet.
- **Theme:** unchanged — still `UiKit.PushWindowTheme`/`PopWindowTheme` around the whole window, so it follows Dark/Light/Neon/Midnight exactly like the main tablet.
- **Content:** still the exact same `module.Draw()` delegate the embedded `AppFrame.DrawModule` calls, still wrapped in `UiKit.SafeDraw` for failure isolation — no second implementation was created.
- One deliberate side effect: the module description text that used to render below the old native title (as a stand-in for a proper header) is gone, since §24's target layout shows header-then-content with no description line. Not a regression — it was working around the absence of a header, and now there is one.

### Verified unchanged this phase

Appearance, Modules Settings page, Diagnostics' overall composition (log list, severity badges, stat cards), Venue/General pages, Home (Operations summary, app grid, icons, frame, chassis branding, no raw diagnostic lines), the venue-themed outer frame, `/venueos`, and multi-window independence — none of these needed or received changes. No backend protocol, module business logic, or donor repository was touched.

### QA performed this pass

Build (Debug + Release) and the full automated test suite (39 tests) both pass. The header, Diagnostics toolbar, and detached-header layouts were re-verified by tracing the same "reserve region first, position in absolute screen space" math used successfully in Phase 3D, plus a targeted grep confirming both `ImGui.Begin` call sites in the plugin use `NoTitleBar`. As with every prior phase, this is code-level verification, not an in-game screenshot pass — the user's own in-game acceptance is the actual final QA gate for this phase, per the brief's explicit instruction not to self-declare the shell frozen here.

## Phase 3D — Header structural rewrite + Settings visual reconstruction

### Header (hard requirement)

`TabletHeader` was rewritten from arithmetic-offset positioning to three explicit, structurally-separated regions:

- **Right** (venue selector, Settings, Close): its screen position is now a pure function of the header's start position and its own fixed width, computed and reserved *before* anything else is drawn. Every control in it is placed with `ImGui.SetCursorScreenPos` to an absolute screen coordinate — not `SameLine()` chaining — so its position cannot be affected by what the left or flex regions contain, at any window width.
- **Left** (Home, brand mark, venue name): unchanged in behavior, always fully shown.
- **Flex** (app breadcrumb, recent-errors indicator): drawn into whatever space is genuinely left between Left and Right, computed from *measured* text widths every frame. It degrades in the required order — breadcrumb drops first, then the error label shortens ("Recent errors — view" → "Errors" → an icon-only dot with a tooltip) — and is additionally wrapped in `ImGui.PushClipRect`/`PopClipRect` scoped to exactly the flex region's bounds, so even if the width math were ever wrong, nothing it draws can visually paint over the reserved Right region. This is the "second line of defense" the brief asked for beyond careful arithmetic.
- The drag handle now only occupies the space genuinely left over *after* the flex content (measured via `ImGui.GetItemRectMax()`, not predicted), so it can never fight the health dot/label for hover or clicks — a real bug caught in review before it shipped.
- Close remains a themed "X" icon button, always in the reserved Right region; clicking it hides the tablet (`open = false`) without touching module state, and `/venueos` recovers it.

### Settings — full visual reconstruction

Rebuilt against the three provided mockup images (Modules, Diagnostics, Appearance) as the visual target, split into one file per page under `Shell/`: `SettingsScreen.cs` (nav shell + router only — no page-specific field knowledge), `VenueSettingsPage.cs`, `AppearanceSettingsPage.cs`, `ModulesSettingsPage.cs`, `GeneralSettingsPage.cs`, `DiagnosticsSettingsPage.cs`.

- **Navigation:** a real left sidebar (`UiKit.NavRow`: icon tile + title + subtitle + gradient selected state) at widths ≥640px content width; reflows to the existing `Forms.Segmented` tab strip below that, per the brief's "reflow, don't overlap" instruction for narrow widths.
- **New shared components** (`UiKit.cs`): `NavRow`, `InfoBanner` (tinted icon-led explanatory card — sized from measured wrapped-text height, since this ImGui binding's `BeginChild` doesn't auto-size to content), `StatCard` (icon + big value + label tile), and `TextInputModal` (the "+ Add Venue" dialog, replacing the old permanently-visible bare input field).
- **Appearance:** four large theme-preview cards (a small drawn mockup of each theme's actual colors, not an anonymous swatch) with a clear selected ring, plus "Active Venue / Theme" context. The "Theme Options" section exposes exactly two toggles — **both real**: `VenueBranding` gained `ShowVenueFrame`/`ShowVenueOsBranding` (bool, default true), persisted per-venue exactly like every other theme value, and `Plugin.Draw` now checks them before calling `UiKit.DrawVenueFrame`/`DrawChassisBrand`. The mockup's "Use venue accent colors" toggle and "UI Scale" slider were **deliberately omitted** — there is no second accent-color source to switch between and no font/UI scaling mechanism exists anywhere in the codebase, and adding a switch that does nothing would be exactly the fake-functionality the brief warned against.
- **Modules:** a real table (icon/name/description, Ready/Disabled status badge, enable toggle, Configure) with top/bottom `InfoBanner`s matching the mockup's instructional copy. "Configure" opens a master-detail view (breadcrumb + "← Back to Modules") that renders the selected module's own `IVenueModule.DrawSettings()` — Settings still has zero hard-coded knowledge of any module's fields, matching §27.
- **Diagnostics:** a real filter toolbar (Log Level, Module, Search — all functional) over a scrollable entry list, plus a bottom stat row (Total/Errors/Warnings/Last Update). Two deliberate departures from the mockup, both to stay honest: there is no fabricated "Information" log level (`DiagnosticsService` only ever records warnings and errors — inventing an INFO stream just to visually match a console mockup would be fake data), and there is no "Export" button (would require file I/O the Shell layer doesn't currently have a safe path for; "Copy" — `ImGui.SetClipboardText` — covers the same need with zero new risk). `DiagnosticsService` gained a real per-entry timestamp (`DiagnosticEntry(Message, At)`, using the same `IClock` pattern already used everywhere else in the codebase) and a `Clear()` method backing the "Clear" button — both genuinely functional, not decorative.
- **Venue:** venue rows as cards (name, Active badge, current theme, Switch/Rename/Duplicate/Delete), "+ Add Venue" now opens `TextInputModal` instead of a permanently-visible input field. Delete confirmation and the "last venue can't be deleted" rule are unchanged.
- **General:** deliberately sparse per §35 — an "About VenueOS" card (version, one-line description) and a pointer to Diagnostics for status data. Module counts/error counts were *not* duplicated here from Diagnostics/Home, since the brief was explicit that pure status information isn't a "setting."

### Verified unchanged

`/venueos` (open/focus/no-duplicate, clean disposal), the detachable-window architecture (`ModuleWindowManager`, one instance per module, independent multi-window, shared `venues.Current`), and the borderless main-window chrome/drag/resize/minimum-size behavior — none of this needed to change this phase, only the header's internal layout math did.

### Layout bugs caught during this pass's own review (not shipped)

- `Forms.ComboField`/`Forms.SearchBox` always forced full-width internally (`SetNextItemWidth(-1)`), which would have made the Diagnostics toolbar's three fields ignore any `PushItemWidth` wrapping and stack incorrectly. Both gained an explicit optional `width` parameter (default `-1`, preserving every existing call site's behavior).
- The same two functions draw a label above the field (two ImGui lines internally); chaining `SameLine()` after a full `ComboField` call aligns the *next* thing with the *field* row, not the *label* row. Fixed by positioning each toolbar column from one shared captured row-top instead of chaining.
- A module's description text could wrap to two lines at narrower widths inside the Modules table; the row-advance height is now computed from the actual measured wrapped height instead of a fixed constant, so rows can no longer overlap their neighbor.

## Phase 3C — Final shell bugfix pass

Two concrete bugs survived Phase 3B's (code-inspection-only, not in-game) QA pass and were reported from an actual running build. Both are now fixed:

- **Raw diagnostic lines on Home:** these were never actually coming from `HomeScreen`/`VenueOperationsDashboard` (which have shown only compact badges since Phase 2) — they came from a separate, previously-overlooked loop at the bottom of `Plugin.Draw()` that rendered `notifications.Toasts` as raw `ImGui.TextColored` lines, unconditionally, under *every* screen (Home, Settings, any module). Removed entirely. No data was lost: both example cases the report cited — module-failure messages and venue-config recovery warnings — were already independently captured in `DiagnosticsService`/`VenueProfileService.RecoveryWarnings` (via `modules.ModuleFailed` calling both `diagnostics.RecordFailure` *and* the now-removed `notifications.Push` — the toast push was always a redundant second copy) and are still fully visible, with secrets still redacted, in Settings → Diagnostics and via the header's health indicator / Home's compact error badge.
- **Header right-cluster overlap — actual root cause:** `TabletHeader` was computing its right-side layout (health indicator, venue selector, Settings, Close) from `ImGui.GetWindowWidth()`, but `ImGui.SameLine`'s offset parameter (and `SetCursorPosX`) are measured from the *content region's* left edge — a frame that excludes window padding on both sides. `GetWindowWidth()` includes both, so every right-cluster offset was systematically ~1–2 padding-widths further right than the content region actually extends, meaning the cluster could render partly outside the header's own background card and the window's true content bounds. Fixed by reusing the already-correct `width` value (`ImGui.GetContentRegionAvail().X`, captured once at the very start of the header before any cursor movement) as the layout reference instead. The same mistake was also present in `UiKit.DrawChassisBrand`'s text-centering math (cosmetic only — a few pixels off-center, not an overlap) and was fixed the same way. The Phase 3B collapse-priority logic (breadcrumb drops first, then the health-status label text, down to icon+tooltip) is unchanged and still correct — it was the coordinate frame feeding it that was wrong, not the priority logic itself.
- **Lesson for future header/frame work:** always source a "right edge" or "center" reference for `SameLine`/`SetCursorPosX` from `ImGui.GetContentRegionAvail().X` (+ `GetCursorPosX()` if not captured at column 0), never from `ImGui.GetWindowWidth()`/`GetWindowSize()`, which include padding the cursor-position APIs don't.

## Phase 3B — Shell cleanup: Home icon, banner removal, responsive header, venue frame, chassis branding

- **Home icon bug fixed:** the Home button was drawing the `"grid"` glyph — the *exact same* icon Bingo uses — because `TabletHeader` passed `"grid"` as the icon key by copy/paste of the widget id. Added a proper `"home"` glyph to `AppIcons` (a roofline + door silhouette, unlike anything else in the icon set) and pointed the Home button at it. Verified by inspection that no other icon key collides with any other module's key.
- **Large venue banner removed:** `HomeScreen`'s gradient banner (venue name at 1.6× scale + "NEON THEME · VenueOS") is gone entirely — not shrunk, deleted, along with its now-dead `DrawBanner` method and the `VenueProfile venue`/`VenueProfileService venues` parameter that only existed to feed it (removed from `HomeScreen.Draw`'s signature and its `Plugin.cs` call site). The vertical space it used is not replaced by an empty region — the overview card and app grid simply start higher, reclaiming it. Venue identity is not duplicated: the venue name lives in `TabletHeader` only; the theme name is not shown prominently anywhere on Home (it remains visible/editable in Settings → Appearance, unchanged from Phase 2).
- **Top bar overlap — root cause found and fixed:** the Phase 3 header positioned its right-hand cluster (health indicator, venue selector, Settings, Close) using *fixed* offsets from the right edge (`rightEdge - 335`, `rightEdge - 195`, etc.). Those offsets assumed the left-hand content (venue name + app breadcrumb, e.g. "TournamentControl") would never be long enough to reach them — for long venue names or long module names, the left content could run past where the right cluster was told to start, pushing (or clipping) the venue selector/Settings/Close past the actual window edge. `TabletHeader` was rewritten so every right-cluster offset is computed from **measured** widths (`ImGui.CalcTextSize` for text, known constants for buttons/combo, `ImGui.GetStyle().ItemSpacing.X` for real item spacing) every frame, with an explicit collapse order matching §30's priority list: the app breadcrumb drops first (it isn't in the priority list at all), then the health-status *label* text drops to an icon-only dot with a hover tooltip — Home, the venue name, the venue selector, and Settings are never dropped or allowed to overlap. The drag-handle's gap width is derived from the same live measurements, so it never overlaps a control either.
- **Venue-identifying frame:** `UiKit.DrawVenueFrame(theme)` draws a two-tone border (`theme.Tokens.Accent` outer ring, `theme.Tokens.Primary` inner ring, both semi-transparent) directly at `ImGui.GetWindowPos()`/`GetWindowSize()` — read fresh every frame, so it tracks resizing and dragging automatically with zero stored state. It's the first thing drawn after `ImGui.Begin` succeeds in `Plugin.Draw`. Every venue is visually distinguishable by its own Accent/Primary pair without consuming any layout space, since it's an overlay on the window's own draw list, not a widget. It only reads semantic theme tokens — no hard-coded color — so it looks correct (and was reasoned through, not screenshotted, for) Dark/Light/Neon/Midnight. It is a pure decorative overlay, so nothing about its design blocks a future image-based venue background from occupying the same window bounds.
- **Bottom `VenueOS` chassis branding:** `UiKit.DrawChassisBrand(theme)` renders a small, 50%-alpha "VENUEOS" centered in a dedicated strip. `Plugin.Draw`'s content child height changed from `(0, 0)` (fill everything) to `(0, -22)` (fill everything *except* the last 22px), so the brand text has its own reserved space below the scrollable content — it cannot overlap module content, Home, or Settings, and needs no per-screen changes to keep working.
- **`/venueos` verified:** unchanged from Phase 3 — still the sole reopen/focus path, still disposed on plugin unload, still incapable of producing a duplicate main window (see the Phase 3 section below for the mechanism).
- **Detachable windows verified:** unchanged from Phase 3 — `ModuleWindowManager` behavior, one-instance-per-module focusing, multi-window independence, and the shared `venues.Current` context are all as documented below; nothing in this pass touched that code path except that `AppFrame.DrawModule`'s pop-out button continues to work identically since its call site in `Plugin.cs` was untouched.
- **Display names re-verified:** grepped the whole `VenueOS.Plugin`/`VenueOS.Modules.Operations` tree for `"Announcements"`, `VenueBingo4All`, `VenueRaffle4All` — zero matches; `ShoutRunner`/`Bingo`/`Raffle`/`Mair's Trivia` are the only names present. These were already corrected in Phase 3; this pass only confirmed no regression.
- **Settings architecture re-verified:** the Modules-tab per-module "Configure" expander (calling `IVenueModule.DrawSettings()` generically) from Phase 3 is unchanged and still the intended contribution point for future per-module configuration pages.
- **Final raw-ImGui audit:** re-grepped every file in `VenueOS.Plugin` (outside `Shell/`, where the component library itself legitimately calls raw ImGui) for `ImGui.Button`/`InputText`/`InputInt`/`Combo`/`Checkbox` — zero matches, same clean result as Phase 2/3.
- **Responsive/theme QA:** performed by tracing the layout math by hand for representative cases (short and long venue names, with and without a long breadcrumb, at the 900px minimum width and wider) rather than by screenshot, since no live game session is available in this environment — the header's collapse behavior was verified analytically to degrade in the documented order without overlap. All new draw calls (frame, chassis brand, header) read only `theme.Tokens`/`theme.Metrics`, so theme coverage follows directly from that fact rather than needing a separate per-theme check. A live in-game visual pass is still recommended before treating this as fully verified, and is called out below as the main remaining risk.

## Phase 3 — Shell finalization, detachable windows, naming

- **`/venueos` command:** registered in `Plugin.cs` via `ICommandManager.AddHandler`/`RemoveHandler` (added/removed alongside the existing `Draw`/`Update` handler wiring, same lifecycle). Running it sets `open = true` and a one-shot `focusRequested` flag that triggers `ImGui.SetNextWindowFocus()` on the next frame, so it both reopens a closed tablet and brings forward an already-open one — never creates a second window, since `open`/the window's stable ID are singletons on the one `Plugin` instance.
- **Borderless main window:** `Plugin.Draw()` now calls `ImGui.Begin` with `ImGuiWindowFlags.NoTitleBar | ImGuiWindowFlags.NoCollapse`. The native title bar is gone; `TabletHeader` is the only visible chrome. The window's ImGui identity is now `"{shell.Header}###venueos-main-tablet"` — a stable `###` suffix — so switching venues (which changes the human-readable label baked into `shell.Header`) no longer resets the window's remembered position/size, matching the same stabilization already used for detached windows.
- **Custom drag/close:** `TabletHeader` no longer renders inside a `BeginChild` (it draws its rounded background directly via the draw list and lays out its row with manual `SetCursorScreenPos`/`SameLine`), specifically so its drag handle can call `ImGui.SetWindowPos` against the *real* main window rather than a child region — `ImGui.SetWindowPos` always targets "the current window," so the drag logic could not live inside a child without this change. The empty gap between the breadcrumb and the health indicator is an `InvisibleButton`; dragging it moves the window via `GetMouseDragDelta`/`SetWindowPos`/`ResetMouseDragDelta`. A new "close" icon button (`AppIcons` gained a `"close"` glyph) sets `open = false`; recoverable with `/venueos`. Native resize borders are untouched (no `NoResize` flag), so resizing still works with no title bar.
- **Detachable module windows:** new `Shell/ModuleWindowManager.cs`. It owns a `HashSet<string>` of which module IDs are currently detached; `Open(id)` adds to the set and requests focus (so calling it on an already-open module focuses it instead of creating a duplicate), `Close(id)` removes it. `DrawAll` is called once per frame from `Plugin.Draw()` — **before** the `if (!open) return` check for the main tablet, so detached windows keep working even while the tablet itself is closed. Every detached window calls the exact same `module.Draw()` delegate the embedded `AppFrame` calls — per §6, there is only ever one module UI implementation; `ModuleWindowManager` and `AppFrame` are two different thin chrome layers around it. Detached windows keep their native ImGui title bar/close-X/resize (only the *main* tablet's chrome was required to disappear) and use `UiKit.PushWindowTheme`/`PopWindowTheme` (new, factored out of what `Plugin.Draw` already did) so they share the exact tablet theme and rounding.
- **Pop-out control:** `AppFrame.DrawModule` now takes a `ModuleWindowManager` and renders a `popout` icon button (new `AppIcons` glyph) in the embedded header's top-right, tooltipped "Open in separate window," highlighted when that module is already detached. Settings has no pop-out control — it isn't a `ModuleHost` module and detaching it wasn't requested.
- **Failure isolation:** new `UiKit.SafeDraw(theme, diagnostics, moduleId, draw)` wraps `module.Draw()` in both `AppFrame.DrawModule` (embedded) and `ModuleWindowManager` (detached) with a try/catch that records the failure via `DiagnosticsService` and renders a themed `ErrorState` instead of propagating — mirroring the isolation `ModuleHost` already applies to Tick/Init/VenueChanged, extended to Draw. A crash in one module's UI can no longer take down the tablet, another detached window, or another module.
- **Active venue context:** unchanged and single-sourced — `ModuleWindowManager` holds the same `VenueProfileService` singleton as everything else; a detached window's title (`"{ModuleName} — {venues.Current.DisplayName}"`) and the module content it renders both read `venues.Current` fresh every frame, so switching venues updates every open window (main tablet, every detached module, Settings) simultaneously with no per-window venue state anywhere.
- **Detached window position/size persistence:** intentionally relies on ImGui's own per-window-ID position/size memory (the stable `###venueos-detached-{moduleId}` suffix) rather than a custom persistence layer — satisfies the brief's "if current infrastructure already provides sensible persistence, use it; don't build fragile persistence for its own sake." This persists for the running session; whether it survives a full game/plugin restart depends on whether Dalamud's ImGui backend writes `imgui.ini` to disk for this plugin, which was not verified in this environment (no live game session available) — noted as unverified rather than claimed.
- **Window minimums:** main tablet keeps its existing 900×560 minimum; detached windows get a uniform 420×320 minimum (560×480 default). No module's current content genuinely demands a different minimum yet — noted for revisit once a module's reconstructed interior actually needs more room.

Every surface (Home tiles, `TabletHeader` breadcrumb, Settings → Modules list, detached-window titles) reads `ModuleDescriptor.DisplayName` as its single source, so this was a two-line-per-module data fix, not a scattered find/replace.
