# Attendance + Greeter + VIP Reconstruction — Gap Map

Donor reference: `C:\FFXIVplugs\venuestatusandgreet` (read-only; inspected, not modified). VIP has **no standalone donor** — a full-repo grep for `"VIP"` across the donor's source returns zero matches. Its requirements in this pass come entirely from the reconstruction brief itself, not from reconstruction against prior functionality.

## CORRECTION PASS — full standalone parity (supersedes the deferrals below)

The first version of this document (everything from "Standalone Attendance functionality" through "Shared-service changes" below) shipped a deliberately scoped-down Attendance/Greeter: no persistence, a fixed five-preset Greeter instead of a saved-preset library, and no Venue Details/address/export/history UI. **That scope-down was rejected** — the brief that produced this correction pass revoked it explicitly and required full parity. It is kept below, unedited, as an honest record of what was tried first and why; it is no longer the current state of the codebase. This section describes what actually changed to reach parity.

- **Persistence**: `SqliteVenueDatabase` (`VenueOS.Services/AttendanceStore.cs`) — Microsoft.Data.Sqlite **10.0.11** and ClosedXML **0.105.1** (both pulled fresh from NuGet during this pass; both are current stable releases as of 2026-09-04, and NuGet's own vulnerability audit ran clean for both at restore time — replacing the donor's pinned, advisory-flagged Microsoft.Data.Sqlite 9.0.3 / ClosedXML 0.104.2). One long-lived `SqliteConnection` per plugin instance (not one connection per call, as the donor did) so the same connection string works for production (a file at `<PluginConfigDirectory>/attendance.db`) and for tests (`Data Source=:memory:`, which only stays alive as long as one connection holds it open). Every table gained a `venue_id` column the single-venue donor never needed; there is otherwise a direct table-for-table correspondence with the donor's schema (`venue_nights`→`visitor_night_stats`/`guest_samples` for calendar-night aggregates, `venue_sessions`→`session_visitors`/`session_guest_samples` for one opening, `greet_presets`/`hotbar_slots` for Greeter). No schema-migration machinery exists yet beyond `CREATE TABLE IF NOT EXISTS`, since there is only one schema version so far; the donor's own `EnsureColumnExists`/`ALTER TABLE` pattern is the obvious extension point when a second version is needed. The donor's `venue_name`/`venue_address` columns were dropped entirely rather than ported — venue identity is `VenueProfile.Name` (never duplicated) and the address string lives in `AttendanceSettings` (persistent Settings config) instead of being redundantly stamped on every DB row.
- **Attendance**: `AttendanceService` (`Operations.cs`) now owns a real session ("opening") lifecycle — Start/Pause/Resume(id)/Close/Close(id)/Delete(id), backed 1:1 by `IVenueDatabase`'s session methods — plus `FirstVisitTonight` (per-calendar-night, not per-session, matching the donor's `VisitorPresenceChange.IsFirstVisitTonight` exactly), Tonight Summary/Visitors/Samples, cross-night daily stats for the Max/Min comparison, and `.ExportRange` via the new `AttendanceExportService`. `DetachSession()` runs on every venue switch and touches only runtime state — the donor never auto-resumes a session on its own, so neither does this; a session left open when you switch away simply stays "resumable" in its own venue's history.
- **Greeter**: `GreeterService` no longer owns a `List<GreetingPreset>` of exactly five. It owns an `ActivePresetId` (persisted) and reads/writes an arbitrarily-sized preset library plus five hotbar-slot→preset-id assignments through `IVenueDatabase` — donor parity (`greet_presets`/`hotbar_slots`), reversing the earlier pass's fixed-five-slots decision. `GreeterSettings` shrank to the three simple values that don't belong in a database (`AutoGreetEnabled`, `GreetDelaySeconds`, `Enabled`) plus the persisted `ActivePresetId`.
- **Auto Greet First Visit Tonight**: new. `AttendanceService.FirstVisitTonight` is wired (in `Plugin.cs`) to `GreeterService.QueueGreeting` when `GreeterSettings.AutoGreetEnabled` is true, excluding the operator's own character (donor: `Plugin.OnFirstVisitTonightDetected`'s `IsLocalPlayer` check) — the operator is still tracked/counted like any other guest, just never auto-greeted. This **replaces** the previous pass's behavior where *every* arrival (VIP or not) was unconditionally queued for greeting the instant `VipOrchestrationService` saw it.
- **`VipOrchestrationService.OnArrival` narrowed accordingly**: it now only acts on arrivals that match an *enabled* VIP record (`if (vip is null) return;`) instead of calling `GreeterService.QueueGreeting` for every arrival unconditionally. VIPs are still greeted on **every** arrival regardless of `AutoGreetEnabled` or first-visit status (their own dedicated code path, independent of Auto Greet) — the required VIP/Greeter ordering itself (private tell → normal greeting → public shout/yell → greeted) is completely unchanged and re-verified by tests below.
- **UI**: Attendance's operational app gained the donor's Live/Visitors/History/Analytics structure (was: one flat guest list); its Settings gained Venue Details (address + auto-detect), Stats poll interval, and the presence-filtering controls that already existed. Greeter's Settings gained the full saved-preset library (create/edit/delete, independent of the five slots) and hotbar-slot assignment (was: editing the five fixed presets in place); its operational app is unchanged (hotbar + queue/status). See "UI implementation" further below for the full list.
- **What's still not reproduced, and why**: Donor's "Examine"/"Adventure Plate" visitor context-menu actions (`Plugin.ExamineVisitor`/`ShowAdventurePlate`) require internal Dalamud agent pointers (`TryOpenExamineViaAgent`/`TryOpenCharaCardViaAgent`) that nothing else in VenueOS uses and that cannot be verified without a live game session; "Target" and "Mark Greeted" were implemented as the two available Tonight-Visitors row actions instead. This is a genuine, narrow, reported gap — not a silent omission — and is the one piece of the original Attendance donor surface this correction pass did not bring back.

## SECOND CORRECTION PASS — three real bugs found by live testing, root-caused and fixed

Live testing of the first correction pass surfaced three concrete failures. All three were root-caused by re-reading the actual code (not assumed), reproduced with a new automated test each, and fixed. None required donor modification.

### Bug 1: Attendance never populated guests already standing in the venue when an opening started

**Symptom reported**: the operator started an opening while standing inside the venue; their own character (and anyone else already inside) never appeared in Visitors.

**Root cause**: the donor's `VenueTrackerService.Tick` only scans the object table at all while `VenueOpen == true` — its Tick method returns immediately otherwise. So the *very first* scan after opening naturally treats everyone currently inside as a brand-new arrival (the donor's own `currentlyPresent` HashSet is empty at that point, because nothing was ever added to it while closed), which is what makes "opening populates everyone already there" happen for free in the donor. VenueOS's `PresenceService` is shared across Attendance *and* VIP, so it scans continuously regardless of whether an Attendance session is open (VIP needs arrivals even with no session running) — meaning anyone already standing in the venue had already triggered a presence `Arrived` event long before the operator clicked "Start New Opening," and `PresenceService`'s own `Arrived`/`Departed` diffing logic never re-fires `Arrived` for someone who never left. `AttendanceService.Arrive`'s call to `IVenueDatabase.MarkPresent` — the thing that actually populates the Visitors table — is entirely event-driven off that diff, so it was never being reached for already-present guests, including the operator.

**Fix**: `PresenceService` gained `ResetKnownPresence()` — clears what it currently knows is present, with no `Departed` events, so the very next `Tick` sees everyone currently observed as new-since-empty and fires `Arrived` for each of them (the same effect the donor gets from "scanning didn't happen at all while closed," reproduced explicitly instead of relying on an architectural accident that doesn't exist here). `AttendanceService.StartSession`/`ResumeSession` both call it, and both raise a new `SessionOpened` event. Since VIP's own arrival handler guards against re-processing the same guest twice via a `processed` HashSet, `VipOrchestrationService` gained a narrower `ResetProcessed()` (clears just that guard, unlike `ResetForVenue()` which also cancels in-flight chat/awaiting-public state) so an already-present VIP is recognized on the same opening instead of being silently skipped as "already handled." `Plugin.cs` wires `attendanceService.SessionOpened += () => { presence.ResetKnownPresence(); vipService.ResetProcessed(); };` — one coordinated reset, not three independent ones. The operator's own character was never excluded from this path (it never was, and still isn't) — only from Auto Greet.

Covered by three new tests: guests already present get seeded on the next scan after `StartSession` (and are *not* double-counted on a further scan while still present), an already-present VIP is recognized again after the reset, and a guest still present through a Pause→Resume cycle is correctly re-counted as a fresh visit (matching the donor's own Pause-marks-everyone-absent semantics, verified separately at the persistence layer in `AttendanceStoreTests.cs`).

### Bug 2: the VIP "+ Add VIP" button was invisible

**Symptom reported**: the VIP app's empty state said `Use "+ Add VIP" to enable entrance recognition`, but no such button was visible anywhere.

**Root cause**: `Forms.SearchBox` defaults to `width = -1`, which tells ImGui to consume *all* remaining horizontal space in the current row. `VipOperatorPanel.Draw()` called `Forms.SearchBox(...)` (default width) immediately followed by `ImGui.SameLine(); UiKit.PrimaryButton(theme, "+ Add VIP")` — since the search box had already claimed the entire row's width, the button was positioned past the actual right edge of the card and rendered off-screen (or clipped to nothing), not merely "hard to see." This is the exact class of bug this codebase has hit and fixed before (`TabletHeader`, the Diagnostics toolbar) and is called out in `UI_STATUS.md`'s own lesson from Phase 3C: *"always source a width/position for `SameLine`/`SetCursorPosX` from measured/reserved space, never assume a preceding full-width field left room."* The button, the modal it opens, and the whole Add/Edit flow were otherwise already fully implemented and correct — this was a pure layout bug, not a missing feature.

**Fix**: reserve the button's width first (`ImGui.GetContentRegionAvail().X - buttonWidth - ItemSpacing.X`) and pass it explicitly to `Forms.SearchBox`, then give the button an explicit fixed width instead of an implicit auto-size — the same "reserve the critical region first" pattern already used everywhere else in this codebase.

### Bug 3: Greeter's saved-preset library had the identical bug on its "New Preset" button

**Symptom reported**: "no usable saved-preset library and no usable workflow for assigning saved presets to hotbar slots."

**Root cause**: identical to Bug 2 — `GreeterOperatorPanel.DrawSettings()`'s Saved Presets section had `Forms.SearchBox(...)` (default full width) immediately followed by `ImGui.SameLine(); UiKit.PrimaryButton(theme, "New Preset")`, pushing "New Preset" off the visible card. The Hotbar Slot Assignments section (five `Forms.ComboField`s) and the preset editor below it were unaffected — only the button to start a brand-new preset was invisible, which made the whole library feel non-functional even though editing/deleting an *existing* preset (once one somehow existed) worked.

**Fix**: identical to Bug 2 — reserve the button's width first.

### Bug 4 (a design gap, not a rendering bug): manual "Mark as Greeted" existed but didn't touch Greeter's authoritative state

The first correction pass's Attendance Visitors row already had a "Mark Greeted"/"Mark Not Greeted" button, but it only ever wrote the persisted display flag (`IVenueDatabase.MarkGreeted`) — it had no effect on `GreeterService`'s actual `greeted`/queue state, so a manually-marked guest could still be auto-greeted afterward, and there was no way to pull a pending/in-flight guest out of the queue from Attendance. This is new work, not a bug fix to something that was claimed complete before: `GreeterService.MarkGreeted(GuestIdentity, bool)` is now the single authoritative mutator (removes a pending guest from the queue, cancels them if they're the in-flight job, and — going the other way — makes a guest eligible again), `AttendanceService` gained an optional `GreeterService?` dependency and its own `MarkGreeted` now calls both the DB (display) and `GreeterService.MarkGreeted` (authoritative), and the Attendance Visitors row gained a right-click context menu (Target/Mark as Greeted) alongside the existing button, plus an explicit "Greeted"/"Not Greeted" `StatusBadge` so the state isn't communicated by color alone.

## THIRD CORRECTION PASS — Greeter-only: the actual crash behind "no usable preset library"

A targeted Greeter correction pass followed the second one, reporting the saved-preset library, editor, and hotbar assignment as still non-functional. Re-reading `GreeterOperatorPanel`/`GreeterService`/`SqliteVenueDatabase` line by line (not trusting that the second pass's own fixes were sufficient) found one real remaining bug, distinct from the two `SameLine()`-width bugs already fixed:

**Bug: saving a second preset with a name already used in the same venue threw an unhandled `SqliteException`.** `greet_presets` was created with `UNIQUE(venue_id, name)`, but `SqliteVenueDatabase.SavePreset`'s insert path (used for every "New Preset" save) was a plain `INSERT` with no conflict handling — colliding names threw straight up through `GreeterService.SavePreset` → `GreeterOperatorPanel.DrawSettings()`, where `UiKit.SafeDraw` (wrapping every module's render call) caught it and replaced the *entire* Greeter Settings screen with a generic error card. From the operator's perspective this looks exactly like "there is no preset editor, no library, no hotbar assignment" — the whole screen is gone, not just the one action that failed. This is a very easy bug to hit by accident (two presets both named "Test," or the same test name reused across two creation attempts) and would explain both this pass's report and, in hindsight, plausibly the prior pass's report too.

**Fix**: the `UNIQUE(venue_id, name)` constraint was dropped — `Id` is already the real stable identity used everywhere (hotbar assignments, edit-in-place, delete), and nothing actually requires preset names to be unique; two presets can legitimately share a display name without any correctness issue. Since `CREATE TABLE IF NOT EXISTS` is a no-op against a database file that already has the old schema (from any earlier build), a real migration was added: `SqliteVenueDatabase`'s constructor now checks `sqlite_master` for the old constraint on startup and, if found, rebuilds the table (foreign keys off around the rename, per SQLite's own guidance, since `hotbar_slots.preset_id` references it) while preserving every existing row's `Id` — so already-saved presets and their hotbar assignments survive the fix instead of being silently dropped.

Verified with two new tests against real SQLite: saving two same-named presets in one venue no longer throws, and opening a database file seeded with the *old* schema (raw SQL, a separate connection, verifying the exact bug scenario) migrates cleanly and preserves the pre-existing preset. A third new test confirms the same preset can be assigned to more than one hotbar slot (the donor doesn't restrict this, and neither does this schema). Everything else in Greeter — the saved-preset library, editor, five independent hotbar-slot assignments, Behavior section, and the operational hotbar's click-to-activate — was already implemented correctly in the second correction pass; this pass found and fixed the one thing actually preventing it from working.

## Standalone Attendance functionality (`VenueTrackerService.cs`, `Configuration.cs`, `DatabaseService.cs`)

- **Session lifecycle:** `StartVenueSession`, `ResumeVenueSession(sessionId)` (continue a specific past DB session), `PauseVenueSession` (stop tracking, keep the DB session row open/resumable), `CloseVenueSession` (finalize). All four write through to a SQLite-backed `DatabaseService`.
- **Presence filtering, three independent axes:**
  - `LockToOpenTerritory`: when starting a session, captures the operator's **current territory ID at that moment** (not a pre-configured static ID) and rejects/clears presence outside it.
  - `UseDistanceFilter` + `VenueRadiusYalms`: when true and `UseOutdoorVenueArea` is false, the filter center is the **operator's own live position, re-evaluated every scan** (a "stay within radius of me" model — appropriate for indoor housing instances).
  - `UseOutdoorVenueArea`: an alternate mode where the center is **captured once when the session opens** (`OutdoorVenueCenter = objectTable.LocalPlayer?.Position`) and held fixed — for open-world locations where the operator may move around.
- Presence scan interval: 1 second (object-table scan for `IPlayerCharacter`, world resolved via `HomeWorld` falling back to `CurrentWorld`). The operator's own character is **not** excluded from the scan — it can appear in the guest list like any other player. This is existing donor behavior, preserved as-is rather than "fixed."
- `FirstVisitTonightDetected` event — fires from `DatabaseService.MarkVisitorPresent`'s `IsFirstVisitTonight` flag, i.e., "first arrival recorded for this DB-persisted session."
- Persistent history/stats (`DatabaseService`, 1627 lines, SQLite): full night summaries, per-visitor session rows, 5-minute guest-count samples for a line chart, daily stats across a date range, session list/delete, CSV export (`ExportService.cs`), and — notably — **greeting presets and hotbar-slot assignments are stored in the SQLite DB**, not the plugin's JSON config, with a variable-size preset library assignable across a small number of hotbar slots.
- `TrackingPollIntervalSeconds` (default 900s) — cadence for the 5-minute-bucketed guest-count sample used by the history chart, independent of the 1s live presence scan.

## Standalone Greeter functionality (`GreeterService.cs`, `GreetPreset.cs`)

- `GreetPreset`: `Name`, `Line1-3` (tell lines), `Line4` (a **command**, not a 4th tell — sent via `ExecuteStepCommand`, not `SendTell`). Structurally this already matches VenueOS's `GreetingPreset(Name, Line1, Line2, Line3, Command)` exactly.
- Queue: one `ConcurrentQueue`, de-duplicated by a `queuedKeys` set; `QueueGreeting` rejects if no active preset, guest not currently present, or already queued.
- **Per-step presence re-validation**: before starting a job and before *every* step, `canGreetNow(guest)` is re-checked; if the guest left mid-sequence, the job is dropped cleanly (`DropGuest`) rather than continuing to send tells to someone who's gone.
- **Timing:** an initial `GreetDelaySeconds` (0–20, clamped) before the first step, a fixed 2-second gap between steps (`InterStepDelaySeconds`), and — the current VenueOS implementation is missing this — a fixed 2-second gap **between finishing one guest and starting the next** (`InterGuestDelaySeconds`), whether the previous guest finished normally or was dropped.
- Message handling: strips accidental `/tell` prefixes and quote characters from operator-entered text, replaces a `<t>` placeholder with the guest's name, and tries multiple `/tell` command-syntax variants (plain, quoted, `/t` shorthand) until one is accepted by the game, falling back progressively.
- `ActivePresetName`, `PendingGreetingCount`, `GetQueueSnapshot()` for live UI.

## Decisions made this pass (and why) — ⚠ items 1, 2, and 4 are REVOKED by the correction pass above; kept for the record

1. ~~No SQLite/history/stats/export subsystem this pass.~~ **REVOKED.** Full persistence now exists — see "CORRECTION PASS" above (`SqliteVenueDatabase`, `AttendanceExportService`). 3. **Presence filtering is reconstructed as a live, in-memory feature** (no persistence needed): `PresencePolicy` gains an `AttendanceAreaMode` (`FollowOperator` — live recenter on the operator's current position each scan — or `FixedPoint` — captured once, matching the donor's outdoor mode), `PresenceService.Tick` gains an optional live operator-position parameter, and `AttendanceSettings` gains `LockToOpenTerritory`, `UseDistanceFilter`, `AreaMode`, `RadiusYalms`. 4. ~~Pause vs. Close is not reproduced as a distinct state.~~ **REVOKED.** `AttendanceService.PauseSession`/`CloseSession` are now genuinely distinct, DB-backed states (`ClosedAtUtc IS NULL` = resumable/paused, non-null = closed) — see "CORRECTION PASS" above.
5. **Target-fill uses a new minimal shared abstraction**, `ITargetedPlayerProvider` (`VenueOS.Services`), backed by Dalamud's `ITargetManager` in `Plugin.cs` — mirroring the existing `IObjectSnapshotProvider`/`DalamudObjectSnapshotProvider` pattern exactly, so it's testable without Dalamud. 6. **VIP identity (Name/World) becomes editable**, required for target-fill-while-editing to be useful. Handled by tracking the record's original key at edit-start and replacing by that key on save, rather than by the (potentially changed) current key. Still current.
7. **Settings vs. operational split enforced**: Attendance's filtering config, Greeter's full preset library/hotbar assignments, and VIP's recognition-tell template all live in their respective `Settings → Modules → *` `DrawSettings()` views — previously these three modules' `DrawSettings()` all just mirrored `Draw()` (a gap flagged in `NEW_MODULE_GUIDE.md` §8/§21). `AttendanceModule`/`GreeterModule`/`VipModule` gained a second, optional `drawSettings` delegate parameter to support this without touching the other six modules' registration calls. Still current; the correction pass's UI section below adds what actually moved into each `DrawSettings()`.

  - **History**: the list of openings (Resume/Close per resumable row, Delete with confirmation for any non-current row), the Max/Min guest comparison (`UiKit.LineChart`, a new shared component — see below) over an adjustable comparison-day range, the daily-stats table, and Export to Excel (folder text field pre-filled from and saved back to Settings' `ExportDirectory`, matching the donor's own "editable but persisted" behavior for that one field).
  - **Analytics**: tonight's 5-minute guest-count samples as a chart plus the last 20 as a table.
  - **`DrawSettings()`** gained a "Venue Details" section above the existing presence-filtering controls: In-game address (editable), Auto-detect toggle, a "Detect Now" button backed by the new `IVenueAddressProvider`/`DalamudVenueAddressProvider`, and the detected DC/Server/District/Ward/Plot readout — plus a Stats Poll Interval field that now actually drives `AttendanceService.Tick`'s sampling cadence (previously configured but unused).
- **`GreeterOperatorPanel`**: `Draw()` is unchanged in shape (five-slot hotbar + status line) but now reads assignments/active-preset from `IVenueDatabase` instead of a fixed in-memory list, and shows an "Auto Greet ON/OFF" indicator. `DrawSettings()` gained three sections: Behavior (Auto Greet toggle, Greeter enabled, greet delay), Hotbar Slot Assignments (five `Forms.ComboField`s picking any library preset or "(Empty)"), and Saved Presets (a searchable library list with Load-into-editor/Delete per row, a "New Preset" button, and one shared Name/Line1-3/Command editor with Save New/Update).
- **New shared UI component**: `UiKit.LineChart` (`Shell/UiKit.cs`) — a minimal two-series line chart drawn directly on the draw list, the same "reserve the region, draw with absolute screen coordinates" pattern already used everywhere else in this codebase, ported from the donor's own `MainWindow.DrawLineChart`/`DrawSeries` rather than adding an external charting dependency. Used by Attendance's Max/Min comparison and guest-sample charts; available to any future module that needs one.
- **`Plugin.cs`**: added `IPlayerState`/`IDataManager`/`IPluginLog` plugin services, `SqliteVenueDatabase`/`AttendanceExportService`/`DalamudVenueAddressProvider` construction (the database is disposed in `Plugin.Dispose`), the Auto Greet wiring (`attendanceService.FirstVisitTonight += ...`), `IsLocalPlayer`/`TryTargetVisitor` helpers, and `DalamudVenueAddressProvider` itself (ported from the donor's `VenueAddressService`, including its `unsafe FFXIVClientStructs.HousingManager` housing-detail lookup — see the class's own doc comment for why this one piece of unsafe code was judged an acceptable, narrow port rather than a blocker). `VenueOS.Plugin.csproj` gained `AllowUnsafeBlocks` and a reference to `FFXIVClientStructs`, matching the donor's own project setup.

## Manual QA (live-game — not exercised in this environment)

No live FFXIV session is available in this environment (consistent with every prior VenueOS phase's own QA notes), so the following still needs an in-game pass before this reconstruction is considered fully verified. Automated tests cover every piece of business logic that doesn't require Dalamud/ImGui. The second correction pass's own prompt specified three exact, numbered mandatory acceptance scenarios (Attendance: 21 steps including already-present seeding, the operator's own inclusion, and Pause/Resume/Close; Greeter: 13 steps, create-a-preset-through-assign-to-DJ1-through-activate; VIP: 17 steps, the full Add-through-target-fill-through-Remove flow) — those are the primary script to run in-game; the checklists below add further coverage (themes, detached windows, venue switching, export) around them.

### Target-fill ("Use Current Target")

1. Open VIP, click "+ Add VIP" with nothing targeted. Click "Use Current Target." Expect a clear warning ("No target selected.") and no field changes, no crash.
2. Target a non-player object (a piece of furniture, an NPC vendor, a housing item). Click "Use Current Target." Expect "Target is not a player character." and no field changes.
3. Target a valid player character. Click "Use Current Target." Expect Name and Home World to populate immediately, with no save yet — verify by closing the dialog with Cancel and reopening Add to confirm nothing was persisted.
4. Repeat step 3, then edit the Announcement/Notes/Channel before clicking Add — verify identity fields are not overwritten by anything else and the record saves with everything you entered.
5. Target yourself and use target-fill — expect it to succeed and populate your own Name/World like any other player (self-targeting is not special-cased; verify this is the desired behavior, since the brief listed self-target among cases to "handle gracefully" without specifying the resulting behavior beyond "no crash, no malformed record").
6. Target a player on a different world than you and confirm the correct Home World (not your own) is captured.
7. While the target's name/world briefly can't be resolved (e.g., a player just rendering in, still loading), click target-fill and confirm a graceful "not currently available" message rather than a blank/garbage record.
8. Open Edit on an existing VIP, use target-fill to point it at a *different* character, and confirm the original record is replaced (not duplicated) and still reflects the edited Name/World when you reopen Edit.
9. Use target-fill in Edit but then click Cancel — confirm the original record is unchanged.
10. Add a VIP via target-fill, save, then immediately have that same character arrive in-venue — confirm the recognition tell and public announcement both fire using the just-saved identity.
11. Attempt target-fill with no VIP module Settings configured (default `RecognitionTemplate`) — confirm Add/Edit still works independently of Settings state.
12. Confirm the "Use Current Target" button's tooltip text is legible in all four built-in themes.
13. Confirm repeated clicks of "Use Current Target" while the same player stays targeted do not queue duplicate work or cause flicker — it should just refresh the same two fields each click.

### Full module QA (session start through venue switch)

1. Start a venue session in Attendance with default Settings (territory lock on, distance filter on, Follow-me mode). Walk guests in and out of radius; confirm the guest list updates and departures fire when a player leaves the object table or the radius.
2. Switch distance-filter mode to Fixed-point, restart the session in an open-world venue, walk away from the captured center yourself, and confirm the radius does not follow you (guests near the original center still count; guests near your new position who are outside the original radius do not).
3. Disable distance filtering entirely and confirm every player in the territory counts regardless of distance.
4. Set an active Greeter preset with all four content fields (Line1–3, Command) filled in via Settings, have a guest arrive, and confirm all three tells plus the command fire in order with the documented 2-second gaps.
5. Queue two guests back-to-back and confirm the 2-second inter-guest delay is visible between the first guest's completion and the second guest's first tell.
6. Have a guest leave mid-greeting (zone out or walk out of range) and confirm the sequence stops cleanly with no further tells to them and no "greeted" credit.
7. Add a VIP (with target-fill), have them arrive, and confirm the order: private recognition tell → normal Greeter tells → VIP's public shout/yell → guest shows as greeted in Attendance.
8. Disable that VIP and have them arrive again in a new session — confirm no VIP tell/announcement fires. Separately, confirm a *regular* (non-VIP) guest's normal Greeter flow still fires on their first arrival of the night when Auto Greet is enabled (see the new Persistence/Auto Greet section below for the full check).
9. Remove a VIP with the confirmation dialog open, verify it shows `Name @ World`, cancel it once to confirm nothing is removed, then confirm it for real.
10. Switch to a second Venue Profile mid-session and confirm: Attendance's guest list clears and its Settings (territory lock/radius) reload from the new venue, Greeter's active preset and hotbar reload from the new venue (no leftover preset names from the first venue), and the VIP roster reloads to the second venue's own list (empty, if none configured there) with no leakage from the first venue.

With Auto Pop-Out on, open all three and confirm each opens its own detached window (not a duplicate on a second click), the main tablet stays on Home, each detached window's Settings gear correctly opens Settings → Modules → that module, and Close on a detached window only closes that window (module state and the main tablet are unaffected).
