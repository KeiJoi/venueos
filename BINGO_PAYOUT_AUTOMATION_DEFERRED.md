# VenueBingo4All payout automation — status

**Superseded in part.** A full forensic audit (`docs/BINGO_FORENSIC_AUDIT.md`) traced the standalone plugin's autopay to a specific, reproducible repeat-payout bug (its payout ledger is process-memory-only and is explicitly cleared on room rejoin, while the backend has never tracked payout state at all), and a safe reconstruction has since been implemented per the audit's recommended design (`docs/BINGO_V2_PROTOCOL.md` for the backend-authoritative payout ledger; `BingoPayoutOrchestrator`/`IBingoPayoutAutomation`/`BingoPayoutAutomationService` for the VenueOS state machine).

What now exists:
- A backend-authoritative payout ledger (`payout_obligations`/`payout_attempts` tables, idempotent attempt creation, and a guarded confirm transition that can never double-apply `confirmedPaid`) — this is what makes a crash/host-handoff resumable from the exact outstanding remainder instead of from scratch.
- `BingoPayoutOrchestrator` (`src/VenueOS.Modules.Operations/Bingo/BingoPayoutOrchestrator.cs`): pure, unit-tested orchestration enforcing "ambiguous does not mean unpaid" (no auto-retry on an inconclusive outcome), a durable per-attempt backend identity, and re-deriving outstanding from the backend after every confirmed chunk rather than a local counter.
- `BingoPayoutAutomationService` (`src/VenueOS.Plugin/Bingo/BingoPayoutAutomationService.cs`): the real, unsafe ECommons/FFXIVClientStructs trade-automation engine, gated behind the `IBingoPayoutAutomation` interface so the orchestrator is testable without a live game.

**Release status (0.2.0):** Bingo's core functionality — room/game lifecycle, players, paid/complimentary cards, short links, calling, the Called Numbers and Card Viewer windows, and the Payout Ledger display — has completed live QA and is no longer `UnderDevelopment`; it now ships enabled by default alongside VenueOS's other release-ready modules.

**Automated payout remains a deliberately conservative, experimental convenience feature**, not a fully production-verified path. A live self-trade test intentionally probed for abuse: the attempt did **not** falsely report success — it went `Ambiguous`, `Settings → Diagnostics` recorded `games.bingo: payout attempt threw (Not on main thread!)`, and no unintended payout occurred. That result is consistent with the orchestrator's design (an inconclusive outcome is never guessed as paid), but it also confirms the automation engine's game-facing assumptions (trade addon node paths/button text, the exact "Trade complete."/"Trade canceled." chat-text stability across locales, `/dice` chat output format, and correct-thread dispatch) have not yet been exercised cleanly against a live game client — every such assumption is still called out at its exact call site in `BingoPayoutAutomationService.cs`. Hosts should treat "Attempt Payout" as optional, verify trade results manually, and use the Payout Ledger's manual "Mark Paid"/"Mark Not Paid" reconciliation (or another established payout workflow) for anything the automation reports as `Ambiguous` or that they have not independently confirmed.
